# HARPP CMS Assistant — ModSecurity Allowlist on Bluehost (Remediation)

The HARPP CMS Assistant talks to the CMS over the public API at
`https://ikabudkernel.com/api/v1/cms/*` using a Bearer service token.

## Verified facts (2026-09-01)

- The live host is **nginx/1.29.8 reverse proxy → Apache backend**.
- **Apache Mod_Security is active** and returns
  `406 Not Acceptable` ("This error was generated by Mod_Security.") for
  **all cookie-less `POST` requests** — this is HOST-WIDE, not just the CMS:
  verified 406 on `POST /api/v1/cms/content`, `POST /api/v1/harpp/auth/login`,
  `POST /api/v1/export`, and even the public form `POST /cms/login`. GET and
  PUT/PATCH pass (they reach the app; the app returns 401/404, not the WAF).
- The browser admin UI's POSTs pass only because they carry a **real session
  cookie**; the WAF treats cookie-less POSTs as cross-site/CSRF attempts.
- The `Authorization: Bearer` header **does pass through** nginx → Apache → PHP
  (confirmed by the app's own diagnostics) — it is only the POST *method* the
  WAF blocks without a session cookie.

## Why the assistant hit this

The assistant is authenticated by a **Bearer service token in a header** — it has
no browser session cookie. ModSecurity's cookie-less-POST rule can't see the
Bearer token as valid auth, so it blocks the writes. CSRF does not apply to
Bearer requests (a Bearer token is non-ambient and can't be attached
cross-origin), so the app-level auth + capability checks are the real security
boundary and they are enforced (fail-closed).

## Current mitigation (shipped)

`modules/cms/routes.php` registers **PUT aliases** for the write endpoints the
assistant uses (content create/update, builder save) mapping to the same
handlers, and `cms_client.py` uses PUT. This unblocks the assistant today
without weakening app-level auth. The handler CSRF check is skipped for
service-token requests (Bearer is non-ambient) but auth/caps remain enforced.

## Proper fix — allowlist the service-token requests (Bluehost)

Do **not** disable ModSecurity globally (that weakens the whole site). Allow
just the authenticated API writes:

> **Note (2026-09-01):** this Bluehost shared plan does **NOT** expose ModSecurity
> in cPanel (the Security section only lists SSH Access, IP Blocker, SSL/TLS,
> Manage API Tokens, Hotlink Protection). ModSecurity is provider-managed, so a
> self-service exception is not possible — go straight to Bluehost support.

1. **Bluehost support (chat/phone)** — the realistic path. Request:
   > *"On ikabudkernel.com, ModSecurity returns 406 Not Acceptable for all POST
   > requests that don't carry a session cookie. Our application's own
   > authenticated API uses an `Authorization: Bearer` header instead of a
   > cookie. Please add a ModSecurity rule exception that permits POST requests
   > carrying the `Authorization: Bearer` header — i.e., do not apply the
   > cookie-less-POST rule to requests that present that header. This is our
   > product's own service-token auth, not a CSRF vector."*
2. If a **managed WAF** (e.g. SiteLock / Bluehost dashboard → Security) is
   available on the plan, add `/api/v1/cms/*` (or the `Authorization` header)
   to its allowlist instead.

### Verify after the allowlist

With a valid service token:

```bash
curl -i -X POST https://ikabudkernel.com/api/v1/cms/content \
  -H "Authorization: Bearer cms_..." \
  -H "Content-Type: application/json" \
  -A "Mozilla/5.0" \
  -d '{"title":"t","body":"b","status":"draft","type":"post"}'
```

- **Before allowlist:** `406` (ModSecurity) — POST is blocked.
- **After allowlist:** `200`/`201` with `{"ok":true,...}` — native POST works.

Once the allowlist is in place, `cms_client.py` can be switched back from PUT to
POST (optional), but the PUT aliases are harmless and can stay.

## Security note

Skipping CSRF for Bearer requests is safe: a Bearer token is placed in the
header explicitly by the client and browsers never attach it cross-origin, so
CSRF does not apply. CSRF is skipped only when the request is **actually
authenticated** as a service user (`cmsIsServiceTokenRequest()`), never merely
because a `Bearer` header is present.

Hardening applied after review (2026-09-01):
- `workflow.transition` was **removed** from the default service-token
  allowlist (workflow transitions are role-based and could otherwise publish/
  schedule). The AI-scheduling branch in `cmsApiContentWorkflowTransition` is
  also gated on `cmsCanPublish()`.
- Service tokens now carry `content.edit_own` (the update handler requires it)
  but still cannot publish: `cmsCanPublish()` is hard-`false` for service users,
  and non-publishers never persist a *published* builder document.
- Editing preserves the existing content status — the assistant never silently
  unpublishes live content, and its task contract restricts it to draft content.
- Note: content create/update API routes were already CSRF-exempt for browser
  sessions (pre-existing); the PUT aliases inherit that. This is only reachable
  cross-origin if `CORS_ORIGINS` is configured — keep it empty/restricted.
