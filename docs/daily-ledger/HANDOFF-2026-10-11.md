### Two definitions that had to be right (both caught by measurement, not reasoning)

1. **"No movement" = no REAL movement.** 207 keys hold 1,215 ledger rows between them with every
   quantity at zero, so the old `COUNT(*)` reported movement where none happened. The query now counts
   only rows with a non-zero quantity — which also makes `movement_rows` honest elsewhere.
2. **A forecast row has NO `sales` key.** `dl_forecastDemand()` consumes the per-cell sales and returns
   them aggregated as `average_sales`; reading `$row['sales']` reads an undefined index. The first
   predicate did exactly that and **dropped branch 8 product 34 AM — a real 8.00/day stream**. The
   reason is now recorded on the function.

A row that MOVED but did not sell is activity and is never excluded: 195 such rows, all 195 survive.

### Architectural correction worth remembering

I first made both the filter and the sort **defaults inside `dl_forecastRows()`**. That looked
harmless and was not: the Overview's aggregate projection calls the same function, so a *display
checkbox on the Forecast page silently changed what the Overview summarized*, and two oracles went red
(`B7 every key with movement gets a row`, `monthly projection omits a product with zero units sold`).
Those assertions were right as written, so the fix went to the source: **both are opt-in in the shared
function, and the page default lives in the handler**. A filter that hides rows belongs where the
hiding is asked for.
